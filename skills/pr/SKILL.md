# /pr

**Steps in TodoWrite.** First action after loading: put this skill's steps into TodoWrite verbatim; a step you will not do stays in the list as `skip: <reason>`, never deleted.

Turn a reviewed change into a merge request the reviewer and the PM can both read.

## Where you are

`openspec/changes/<slug>/report.md` exists (review ran) and has no MR URL yet. If report.md is missing, stop and say `/opsx-workflow:review <slug>` comes first; the Stop hook will say the same. If report.md still lists items under `待修（範圍內）`, stop and say `/opsx-workflow:apply <slug>` comes first; the Stop hook will say the same. If it already has an MR URL, this is an update: push as in step 4, then update the description by step 4b instead of opening an MR. The update path never comments on the issue; step 5b runs only for a new MR. The logic map is different: step 5c runs on both, so the card always has a map of its current head.

Look at the newest `logic-map-undecided-r*` gate in gates.md. If it is open, stop and repeat its question. If it is answered and has no `寫回:` line, run the **Logic map gate answered** step of `../review/SKILL.md` Step 4 first: after an answer the router sends the card here, not back to review. That step may send the card to `/opsx-workflow:apply`; follow it, and come back to /pr only when it says so.

## Steps

1. **Pre-flight.** Not on `main` / `master`. `git status` clean, or say what is uncommitted and stop. Which forge: `git remote -v`; in Acmecorp-AI and Acmecorp-Infrastructure the primary is the `gitlab` remote, `origin` is only a mirror, so push to `gitlab`; elsewhere `origin`. Read `references/mr-note.md`.
1b. **Workplan said no MR.** When the `pr · <slug>` line ends with `（workplan mr: <value>，但 <reason>）`, the workplan expected no MR but the card does not qualify for archive. Reason `mr: <value> 不認得` or `workplan 沒寫 branch`: fix nothing on your own, write a `type: decision` gate in gates.md (question: open an MR or archive without one; evidence: the reason and, when the workplan names a branch, the output of `git rev-list --count <primary remote>/main..<branch>`, since archiving drops any commit it counts) and stop without opening an MR. Any other reason: first `git fetch <primary remote>`, because a stale `<primary remote>/main` makes main's commits look like the branch's own, then check again with `git show-ref --verify refs/heads/<branch>`, `git show-ref --verify refs/remotes/<primary remote>/main` and `git rev-list --count <primary remote>/main..<branch>`. Both refs exist and the count is above 0: the change touched tracked files after all, so open the MR as usual and, in the same run, 刪掉 workplan 這個 PR 的 `mr: none` line. Both refs exist and the count is 0: continue to `/opsx-workflow:archive <slug>` instead of this skill. A ref is still missing: write the same decision gate and stop without opening an MR. When the answer to that gate arrives, apply it to the workplan first, or the card comes back to this gate: to archive, set that PR's `mr:` to `none` and continue to `/opsx-workflow:archive <slug>`; to open an MR, delete the `mr:` line and go on with step 2.
2. **Gather.** `git log <base>..HEAD --oneline`, `git diff <base>...HEAD --stat`, `report.md` (四桶 and ledger verdict), `tasks.md` (每 task 的 編號 and `測試：` path), `proposal.md` (Summary material), `design.md` (D-ids for Reviewer notes), `grill.md` if present. Migrations: anything under `drizzle/`, `alembic/`, `migrations/` in the diff.
3. **Write the description to a file** `openspec/changes/<slug>/mr.md` in the mr-note format. Title = the conventional-commit subject of the branch's main commit, `type(scope): summary`. Changes table rows = tasks, one per task, 編號 = task number, 對應測試 = that task's `測試：` file. Test plan = the test agent's last summary from report.md and the merge-gate command for this repo (`pnpm test:merge-gate` in Acmecorp-AI; see each repo's CLAUDE.md). Reviewer notes = 範圍、rollback / risk when ACL / schema / enforcement paths moved, D-ids that deviated, follow-ups as inbox card slugs. No emoji, no slogans, no bracketed explanations in headers. Before the file is final, `Read ../technical-writing/SKILL.md` and apply it to the description, then `Read ../unslop/SKILL.md` and apply that.
4. **Push and open.** `git push -u <remote> <branch>`, then `glab mr create --title "<title>" -F openspec/changes/<slug>/mr.md --source-branch <branch> --target-branch main` (or `gh pr create --title … --body-file …`). Never `--fill`; the format hook denies an MR without the table. Auto-merge is step 4c. Run every `glab` and `gh` call here, in steps 4b and 4c and in step 5 as its own Bash command, never chained with `;`, `&&`, `||`, `|`, `$(…)` or a trailing `echo exit=$?`: the sandbox exclusions that let them reach the forge are the patterns `glab mr *` and `gh pr *`, and a chained command does not match them, stays inside the sandbox and fails with `x509 … OSStatus -26276`.
4b. **Update the description.** Runs on an update, and when babysit sends a push here. Write mr.md again by step 3, then read the MR's current description (`glab mr view <iid> -F json`, or `gh pr view <n> --json body`). When it is the same as mr.md, stop this step: no update and no gate. Otherwise, on GitHub run `gh pr edit <n> --body-file openspec/changes/<slug>/mr.md`. On GitLab, do not use `glab mr update` for the description: it has no flag that reads a file, and the format hook denies a description passed through a command substitution. Write a `needs: run` gate with a `by: coordinator` line instead, whose 建議 is this one command: `glab api -X PUT projects/:fullpath/merge_requests/<iid> -F description=@<absolute path of mr.md>`, and stop. When the answer comes back, run step 5's read-back. When the read-back lacks `## Changes` or `| 編號 |`, write the same gate again; never try another way of writing the description.
4c. **Auto-merge.** Only when the repo's CLAUDE.md asks for auto-merge, and only on GitLab. After step 4 opens the MR, and after every push babysit makes, read `merge_when_pipeline_succeeds` and `head_pipeline.status` from `glab mr view <iid> -F json`. When auto-merge is on, do nothing. When it is off and the pipeline is `created`, `pending` or `running`, write a `needs: run` gate with a `by: coordinator` line whose 建議 is this one command: `glab api -X PUT projects/:fullpath/merge_requests/<iid>/merge -F merge_when_pipeline_succeeds=true -F sha=<head sha>`. Both parameters are required: `sha=` makes GitLab refuse when the head moved, and the coordinator does not run the command without either. When the pipeline is `success`, write no gate, because that call would merge at once; put `auto-merge: no（pipeline 已綠，等合併）` on the `## MR` line of report.md and leave the merge to the board. When the pipeline is `failed` or in any other state, write no gate and put `auto-merge: no（被取消）` there.
5. **Verify.** `glab mr view <iid> -F json` (or `gh pr view --json body,url`): description length > 0 and contains `## Changes` and `| 編號 |`. A 200 on update can still have written an empty body; read it back. Then append to report.md:

   ```
   ## MR
   <url> · opened <date> · auto-merge: <yes|no>
   ```

   and `opsx status pr 5/5 "MR 已開"`.
5b. **Back-link.** Leave the MR URL on the issue the card came from, only when this run opened a new MR (report.md had no MR URL before step 5) and the card's inbox.md `source:` starts with `gitlab:` or `github:`. Cards from any other source are skipped. Locate the issue through inbox.md's `upstream_url`, not through `source` (its `<repo>` is the local repo name).
   - GitLab: `glab issue note <n> -R <upstream_url without /-/issues/<n>> -m "<mr url>"`, where `<n>` is the `#<n>` at the end of `source`.
   - GitHub: `gh issue comment <upstream_url> --body "<mr url>"`, as its own Bash command for the same reason as step 4: the sandbox exclusion is `gh issue comment *`.

   The comment is the MR link and nothing else; never close the issue or change its labels. If the command exits non-zero, or inbox.md has no `upstream_url` (missing `upstream_url` counts as a failure; do not guess the project), add one line under `## MR` in report.md, `issue 回寫失敗：<reason>` (the first stderr line, or `缺 upstream_url`), and go on to step 6. A failed back-link does not stop /pr: the MR is already open. When the grant hook denies the command, that is a failure too: if the deny message carries `action: mr` (a one-time `mr` grant was used up by step 4), write `issue 回寫失敗：無 mr 授權`; for any other deny, use the first line of the deny message as the reason. Then go on; do not write a gate and do not retry, even though the deny message asks for a gate (apply step 5 names this exception).
5c. **Logic map.** Runs on a new MR and on an update. Review's map step (`../review/SKILL.md` step 1b) already built the map before the reviewers ran; this step only makes sure it shows the current head. The map stays a file in the card directory; never post it to the MR. Read the one line under `## 邏輯表` in report.md. When it is `openspec/changes/<slug>/logic-map.md · <sha>` and `<sha>` equals the first 7 characters of `git rev-parse HEAD`, the map already shows this head; so does a line that starts with `skip：` (the user waived the map, or the card is `mr: none`): continue with step 6 without spawning anything; `skip：mr: none` counts only while the card's PR in `openspec/workplan.yaml` still has `mr: none`. Otherwise (a different sha, a `產表失敗：` line, or no `## 邏輯表` section), run sub-steps 1–4 of `../review/SKILL.md` step 1b, with the `<remote>` from step 1. Step 4 already pushed, so `HEAD` is the MR head. Its sub-step 4 overwrites the whole line, and a failure line replaces it the same way, never under `## MR`. When step 1b stops at a gate, stop here: do not reply and do not continue to step 6, even though the MR is already open. After the gate is answered, run step 1b again first: its opening paragraph continues by the answer. Then continue with step 6 only once the line under `## 邏輯表` names this head or starts with `skip：`; when that run ends and the line still does neither, say so and stop again. After the map is rebuilt, its 範圍外 `沒經過決定` and unclassified items are handled by the 範圍外 half of the **Logic map, undecided** rule in `../review/SKILL.md` Step 4 (open a card with `opsx new`, then `opsx note` unless it merged); in-scope items are not gated here.
6. **Reply.** The URL, the title, what the Test plan says, and the two closing lines (skipped / unchecked / risks). Then continue to `/opsx-workflow:babysit <slug>` per `../../references/continue.md`: invoke it now unless a gate is open. Babysit handles CI and review threads and stops when the card is waiting for the user to merge.

## Guardrails

- Push and MR creation need a level-two grant in autopilot; without one, write a gate and stop here.
- No AI attribution in the title, body, or commits.
- Do not merge. Do not resolve threads. That is `/opsx-workflow:babysit` for comments and the user for the merge button.
