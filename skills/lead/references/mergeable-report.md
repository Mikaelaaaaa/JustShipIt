# 可合併回報範例

協調者寫 SKILL.md「類型 2：可以合併」時照這份的樣子寫。範例資料是虛構的，照抄結構與白話程度，不照抄資料。

規則：

- 開頭一行給合併順序，用 `git merge-tree` 從最新 main 依序疊過。
- 每支 MR／PR 一段，段與段之間 `---`。
- 段頭 `### N. !號　白話標題`，下一行 MR 連結，獨立一行。
- 邏輯表寫成可點的 markdown 連結 `[<卡> 邏輯表](file://<絕對路徑>)`，獨立一行。
- 狀態一行：CI、衝突、邏輯表是否對到 MR 最新 head。對不到時說差的 commit 改了什麼。
- 功能說明白話條列，給沒看過程式的人看。
- 誰設定什麼表、舉例表（你是誰／情況 → 結果）。
- 邏輯圖直接貼在回報裡，不能只給連結。邏輯表落後 head 時，照最新程式重畫並註明。
- 沒有邏輯表的卡（例如只改測試），協調者照 diff 寫功能說明與簡短流程，標「照 diff 寫」。
- 條件表重點只列這支 PR 新增或改動的節點，一句白話。
- 測試一行，⚠ 一段，沒有就寫「無」。

---

## 範例

合併順序是 !301 → !302 → !303，從最新 main 依序疊過不會衝突。

### 1. !301　訂單匯出的整合測試可以重跑

https://forge.example.com/acme/acme-web/-/merge_requests/301

邏輯表全文：

[me-20260110-0930 report](file:///home/dev/code/acme-web/openspec/changes/me-20260110-0930/report.md)

**狀態**：CI 綠，沒有衝突。只改了 1 個測試檔（加 3 行、減 6 行），產品程式沒動，所以沒有產邏輯表。下面是我照 diff 寫的。

**功能說明**
- **原本的問題**：有一個測試在跑的過程中，才把兩筆「同一時間下單」的訂單塞進測試庫，跑完也不清掉。同一個測試庫再跑一次時，前面那個「總共幾筆」的測試會從 2 變成 4，結果就紅了。
- **改法**：這兩筆改在整組測試一開始就先寫好，前面那個測試的預期值改成 4。不管跑幾次，結果都一樣。
- **對使用者的影響**：看不出差別。

**誰設定什麼**：還沒有邏輯表

**舉例**：還沒有邏輯表

**邏輯圖**（照 diff 寫）
```
整組開始 → 寫入 o1–o6 六筆訂單（含兩筆同時間下單的 o5、o6，已存在就略過）
  → 「沒有篩選條件」測試：總筆數 = 4
  → 「同時間在 LIMIT 下順序固定」測試：直接用已寫好的 o5、o6，不再插入
```

**條件表重點**：還沒有邏輯表

**測試**：ring3 order-export.integration。第二次跑不再紅，CI 綠。

**⚠**：無

### 2. !302　按確認鈕時，固定用訂單綁的店家查權限

https://forge.example.com/acme/acme-web/-/merge_requests/302

邏輯表全文：

[me-20260111-1415 邏輯表](file:///home/dev/code/acme-web/openspec/changes/me-20260111-1415/logic-map.md)

**狀態**：CI 綠，沒有衝突。邏輯表做完之後，這支 MR 只多了合進 main 的 commit，自己沒有再改程式，所以邏輯表還是準的。

**功能說明**
- **改了什麼**：以前「這張訂單沒有綁店家」時有一套備用做法：查權限時當成這個人什麼都不能改。現在拿掉這套，一律用訂單綁的那個店家。
- **為什麼可以拿掉**：資料庫規定每張訂單一定綁一個店家，這條備用路本來就走不到。
- **對使用者的影響**：看不出差別。

**誰設定什麼**

| 程式名 | 誰設定 | 業務上是什麼 | 被擋時記成 |
|---|---|---|---|
| `orders.store_id` | 系統，建立訂單時寫入 | 這張訂單屬於哪家店 | 不允許空值 |
| 依人給權限開關 | 部署設定 | 打開才檢查這個人能不能改這張訂單 | — |

**舉例**：小明在後台按某張訂單的「確認出貨」。

| 你是誰 | 結果 |
|---|---|
| 小明是這家店的店員 | 照常出貨（跟以前一樣） |
| 小明不是這家店的店員 | 被拒（跟以前一樣） |

**邏輯圖**（功能 1）
```
按確認 → D1 訂單存在? ─否→ 404
            └是→ D2 要檢查權限? ─否→ 放行 ─┐
                     └是→ 用訂單的店家查權限 ─┤
                          → D3 被拒? ─是→ 拒絕 ─┤
                                     └否→ 放行 ─┤
                                                ▼
                                          出貨
```

**條件表重點**（這支 PR 改到的節點）

| 節點 | 白話 |
|---|---|
| D3 | 以前沒有店家時把權限當成空的；現在直接用訂單的店家查。對任何真實資料，結果都一樣 |

**測試**：pre-merge 的相關測試；CI 綠。

**⚠**：無。邏輯表標著「沒有 design.md，未分類」。

### 3. !303　商品的付款方式全被停用，這個商品就不能買

https://forge.example.com/acme/acme-web/-/merge_requests/303

邏輯表全文：

[me-20260112-1600 邏輯表](file:///home/dev/code/acme-web/openspec/changes/me-20260112-1600/logic-map.md)

**狀態**：CI 綠，沒有衝突。邏輯表比最新 commit f00ba12 晚了一步。那個 commit 修的就是邏輯表那條 ⚠，下面的邏輯圖我照最新程式重畫了。

**功能說明**
- **以前的漏洞**：一個商品如果只收公司停用的付款方式，系統還說它能買。
- **現在的規則**：商品收的付款方式先扣掉地區不支援的、再扣掉公司停用的，一種都不剩就不能買。
- **原因怎麼記**：
  - 被地區拿光的，記「地區」。
  - 被公司停用光的，記「付款停用」。
- **對現有商品的影響**：今天只有「預購券」這個商品的結果會變，其他都一樣。

**誰設定什麼**

| 程式名 | 誰設定 | 業務上是什麼 | 被擋時記成 |
|---|---|---|---|
| 公司停用付款 `disabledPayments` | 公司管理員，付款設定 | 全公司不收的付款方式 | payments_disabled |
| 地區 `region` | 使用者選擇 | 有些付款方式只在特定地區能用 | region |
| 商品收的付款 `acceptedPayments` | 商品設定 | 這個商品收哪些付款方式 | — |

**舉例**：公司停用了「貨到付款」和「轉帳」。

| 情況 | 「預購券」商品 |
|---|---|
| 兩種都停 | 不能買，原因記「付款停用」 |
| 只停一種 | 照常能買 |
| 地區把它的付款方式全拿光 | 不能買，原因記「地區」（最新 commit 修正，以前會錯記成付款停用） |

**邏輯圖**（照最新 head f00ba12 重畫）
```
判斷每個商品 → D1 開關開? ─否→ 只看商品有沒有上架
                 └是→ 算 inRegion（扣地區）、payments（再扣公司停用）
                      → D2 地區拿光它的付款方式? ─是→ 記 region
                           └否→ D3 地區還留有，但公司停用後一種不剩? ─是→ 記 payments_disabled
                                    └否→ 不記
                      → D4 一關都沒被擋? ─是→ 可買 / 否→ 不可買
```

**條件表重點**

| 節點 | 白話 |
|---|---|
| D2 | 新增：地區把這個商品的付款方式全拿掉，算「地區」擋的 |
| D3 | 地區還有留、公司停用之後一種都不剩，才算「付款停用」 |

**測試**：ring0 purchasable，加上新的 purchasable-region.test.ts；CI 綠。

**⚠**：原本那條「地區只剩停用的付款方式時，會錯記成『付款停用』」，已經被 f00ba12 修掉。邏輯表檔案本身還沒重產到這個版本，上面的圖是我照最新程式改的。
